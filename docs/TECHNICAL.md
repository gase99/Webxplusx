## تعاریف تخصصی

| اصطلاح | معادل | توضیح |
|---|---|---|

| **فارسی** | Miter Cut (45°) | برش زاویهٔ ۴۵ درجه — روی نقشهٔ برش با علامت بصری مشخص می‌شود |

## مدل دادهٔ هر ردیف — `src/types/part.ts`

```ts
interface CutPart {
  id: string;
  name: string;          // نام قطعه
  length: number;        // طول (mm)
  width: number;         // عرض (mm)
  qty: number;           // تعداد
  bandLength: 0 | 1 | 2; // تعداد لبه‌های نوار در طول
  bandWidth: 0 | 1 | 2;  // تعداد لبه‌های نوار در عرض
  farsiLength: 0 | 1 | 2; // تعداد لبه‌های فارسی در طول
  farsiWidth: 0 | 1 | 2;  // تعداد لبه‌های فارسی در عرض
  grooveLength: 0 | 1 | 2; // تعداد لبه‌های شیار در طول
  grooveWidth: 0 | 1 | 2;  // تعداد لبه‌های شیار در عرض
}
```

مقدار هر عملیات **۰ = بدون عملیات، ۱ = یک لبه، ۲ = هر دو لبهٔ مقابل** است.
`*Length` لبه‌های موازی با طول و `*Width` لبه‌های موازی با عرض قطعه را مشخص می‌کند.
متراژ نوار، فارسی و شیار با ضرب تعداد لبه در طول همان محور و تعداد قطعات محاسبه می‌شود.

## ساختار جدول — `src/components/DataEntryTable.tsx`

- هدر **دو سطحی**: سطح اول «نام قطعه | طول | عرض | تعداد | نوار | فارسی | شیار» و در سطح دوم،
  هر یک از ستون‌های نوار/فارسی/شیار به دو زیرستون «طول» و «عرض» تقسیم شده‌اند (`colSpan`)؛
  بقیهٔ ستون‌ها با `rowSpan={2}` ادغام شده‌اند.
- ستون **شمارهٔ ردیف** در ابتدا و ستون **عملیات** (تکثیر / حذف ردیف) در انتها.
- هر گروه رنگ متمایز دارد: نوار = سبزآبی (teal)، فارسی = قرمز/رز (rose)، شیار = کهربایی (amber).
- برای هر محور ورودی عددی **۰/۱/۲** وجود دارد؛ کلیدهای ↑/↓ مقدار را تغییر می‌دهند و
  کنار ستون **فارسی** آیکون مثلث/خط مورب + برچسب `۴۵°` دیده می‌شود.
- داده‌ها به‌صورت خودکار در `localStorage` مرورگر ذخیره می‌شوند.

## فاز ۲ — موتور چیدمان چندالگوریتمی — `src/engine/`

موتور از یک الگوریتم ثابت به یک **رجیستری الگوریتم** تبدیل شده است. امضای قدیمی
`calculateLayout(parts, stock, options)` در `src/algorithm.ts` دست‌نخورده باقی مانده
و همان گیلوتینی قبلی را اجرا می‌کند (خروجی برای ورودی یکسان بیت‌به‌بیت تغییر نکرده
است — با تست «پروندهٔ ثابت» کنترل می‌شود).

### رابط مشترک

```ts
interface PackingAlgorithm {
  id: 'guillotine' | 'maxrects' | 'skyline' | 'shelf' | 'optimizer';
  label: string;                       // نام فارسی
  description: string;                 // توضیح فارسی
  variants: { value: AlgorithmVariant; label: string }[];
  slow?: boolean;                      // نیاز به Web Worker/پیشرفت/لغو
  run(context: PackingContext): PackingOutcome;
}
```

`PackingContext` شامل نمونه‌های بازشدهٔ قطعات (`instances`)، ورق، `kerf`،
`allowRotation`، `maxSheets`، انتخاب الگوریتم، `onProgress` و `signal` (لغو) است.
`PackingOutcome` شامل `sheets`، `placements` و `unplaced` است؛ ساخت `LayoutResult`
کامل (خلاصه، درصد پرت/بهره‌وری، متریک‌ها و زمان اجرا) کار مشترک
`finalizeResult()` در `engine/shared.ts` است، پس همهٔ الگوریتم‌ها خروجی یکسان دارند.

### الگوریتم‌ها

| فایل | الگوریتم | یادداشت |
|---|---|---|
| `guillotine.ts` | Guillotine Bin Packing | چهار گزینه: `best-area-fit` (پیش‌فرض و برابر نسخهٔ قبلی)، `best-short-side-fit`، `shorter-leftover-axis`، `longer-leftover-axis` |
| `maxrects.ts` | MaxRects | `best-short-side-fit`، `best-area-fit-mr`، `best-long-side-fit`، `bottom-left` |
| `skyline.ts` | Skyline | `skyline-bottom-left`، `skyline-min-waste` |
| `shelf.ts` | Shelf / NFDH | `shelf-first-fit`، `shelf-best-fit` |
| `optimizer.ts` | Simulated Annealing | درونی: MaxRects یا گیلوتینی؛ بذر (`seed`) و تکرار (`iterations`) برای تکرارپذیری، قابل لغو |

افزودن الگوریتم جدید: پیاده‌سازی رابط + افزودن به `ALGORITHMS` در `registry.ts`.

### قواعد مشترک (نباید نقض شوند)

1. قطعه هرگز از مرز ورق بیرون نمی‌زند.
2. هیچ دو قطعه‌ای هم‌پوشانی ندارد.
3. `kerf` فقط از فضای آزاد کم می‌شود (نه از ابعاد قطعه) و بین دو قطعهٔ مجاور
   حفظ می‌شود.
4. `allowRotation=false` ⇒ هیچ قطعه‌ای چرخیده نیست.
5. `maxSheets > 0` ⇒ بیشتر از آن تعداد ورق باز نمی‌شود و باقی قطعات با دلیل
   `STOCK_EXHAUSTED` گزارش می‌شوند (قطعهٔ بزرگ‌تر از ورق: `LARGER_THAN_SHEET`).
6. `placedCount + unplacedCount = totalParts` و مساحت‌ها با خلاصه هم‌خوان‌اند.

این شش قاعده در `engine/__tests__/invariants.ts` (`checkInvariants`) کدنویسی شده و
روی **همهٔ** الگوریتم‌ها اجرا می‌شود.

### اعتبارسنجی ورودی

`validateLayoutInput()` قبل از اجرا صدا زده می‌شود و خطاها را با کد ماشینی و پیام
فارسی برمی‌گرداند:

| کد | مسدودکننده | معنا |
|---|---|---|
| `INVALID_STOCK` | ✅ | طول/عرض ورق ≤ ۰ یا NaN/∞ |
| `INVALID_KERF` / `INVALID_BAND_THICKNESS` / `INVALID_MAX_SHEETS` | ✅ | مقدار منفی/نامعتبر |
| `NEGATIVE_DIMENSIONS` | ✅ | ابعاد منفی قطعه |
| `INVALID_QTY` | ✅ | تعداد منفی |
| `INVALID_PART_DIMENSIONS` | ✅ | NaN/∞ در ردیف |
| `FRACTIONAL_QTY` | ⚠️ | تعداد کسری؛ به پایین گرد می‌شود و به کاربر هشدار داده می‌شود |
| `EMPTY_PART_DIMENSIONS` | ⚠️ | ردیف تک‌بُعدی؛ نادیده گرفته می‌شود |
| `PART_TOO_SMALL_AFTER_BAND` | ⚠️ | بعد از کسر نوار صفر/منفی می‌شود |

ورودی مسدودکننده هیچ‌وقت به الگوریتم نمی‌رسد؛ `runLayout` نتیجهٔ خالی + گزارش
برمی‌گرداند (بدون پرتاب استثنا) تا رابط کاربری پیام نشان دهد.

### اجرای سنگین در Web Worker

`src/workers/packing.worker.ts` + `src/workers/packingClient.ts`:
حالت بهینه‌ساز در ترد جداگانه اجرا می‌شود (پیام‌های `run`/`cancel`/`progress`/`done`/`error`).
اگر `Worker` در دسترس نباشد یا ساختش شکست بخورد، همان محاسبه روی ترد اصلی انجام
می‌شود (fallback).

## فاز ۳ — نقشهٔ برش (SVG) — `src/components/CuttingMap.tsx`

خروجی فاز ۲ (`sheets`/`placements`) با **SVG** رندر می‌شود؛ واحد مختصات خودِ
میلی‌متر است (`viewBox` برابر ابعاد ورق خام) پس نقشه در هر اندازه‌ای شارپ و با
حفظ نسبت ابعاد دیده می‌شود. با کلیک «محاسبهٔ چیدمان»، نقشه بلافاصله زیر کارت‌های
آماری ظاهر می‌شود (برای هر ورق خام یک نمای مجزا با بهره‌وری/پرت همان ورق).
دکمه‌های زوم (۵۰٪ تا ۳۰۰٪ + بازنشانی) و اسکرول افقی برای ورق‌های بزرگ وجود دارد.

- نقشه **سیاه‌وسفید** است: بدنهٔ همهٔ قطعات سفید با حاشیهٔ مشکی است؛ پرت با
  هاشور خاکستری/مشکی مشخص می‌شود و فاصله‌های باریک بین قطعات همان خوراک تیغه (Kerf) است.
- وسط قطعه فقط نام می‌آید (در قطعهٔ باریکِ عمودی متن ۹۰- درجه می‌چرخد). اندازه‌ها
  کنار ضلع مربوطه نوشته می‌شوند: لبهٔ بالا = اندازهٔ ضلع افقی روی نقشه، لبهٔ راست
  (متن عمودی) = اندازهٔ ضلع عمودی؛ عدد از طول/عرض اصلی قطعه با درنظرگرفتن چرخش
  خوانده می‌شود. اگر جا نباشد عدد یا نام حذف می‌شود و جزئیات کامل همیشه در tooltip
  هر قطعه هست.
- بخش رسم هر قطعه در زیرکامپوننت داخلی `PlacedPart` جدا شده و فلگ‌های کارگاهی
  را از ردیف متناظر قطعه می‌خواند — از روی **اسنپ‌شات لحظهٔ محاسبه**، تا ویرایش
  بعدیِ جدول، نقشهٔ نمایش‌داده‌شده را بی‌صدا تغییر ندهد (همان مکانیزم «نتیجهٔ قدیمی»).

**قرارداد رندر علائم کارگاهی روی نقشه (سیاه‌وسفید، علامت روی خودِ لبه)** —
وسط هر قطعه نام و کنار ضلع‌ها اندازه‌ها می‌آیند و عملیات هر لبه
با `getPartEdgeSides` (همان نگاشت لیبل و DXF، با درنظرگرفتن چرخش) روی خودِ
همان لبه رسم می‌شود؛ بالای نقشه هم کادر «راهنمای علائم لبه» هست (در پیش‌نمایش
صفحه و سند چاپی هر دو):

- **نوار** ← نوار مشکی توپر چسبیده به لبه
- **شیار** ← کانال دو خطی با خط‌چین وسط، موازی لبه و کمی داخل‌تر
- **فارسی ۴۵°** ← خط دندانه‌ای (زیگزاگ ۴۵°) موازی لبه

- اگر یک لبه چند عملیات داشته باشد، علائم به ترتیب نوار ← فارسی ← شیار از
  لبه به داخل چیده می‌شوند. نزدیک ابتدای هر لبهٔ علامت‌دار (وسط لبه جای عدد اندازه است) یک برچسب گرد با حرف
  «ن / ش / ف» می‌آید؛ در قطعات کوچک برچسب حذف و فقط علائم رسم می‌شوند.
- ضخامت علائم با مقیاس ورق و کوچک‌ترین بُعد قطعه تنظیم می‌شود؛ عدد اندازه بعد از
  علائم همان لبه و نام در فضای باقی‌مانده رسم می‌شود تا روی هم نیفتند.
- روی **لیبل چاپی** (`MiniPartDiagram` در `LabelSheet.tsx`) قرارداد جداگانه‌ای
  برقرار است: پیکان بیرون هر لبه + نام عملیات («نوار»/«شیار»/«۴۵°») با نگاشت
  `getPartEdgeSides` از `src/partEdges.ts` — همان ماژولی که DXF هم از آن
  تغذیه می‌شود. نقشهٔ برش برای قرارداد جدید به آن ماژول وابسته نیست.

## فاز ۴ — خروجی‌ها (چاپ نقشه + لیست قطعات / DXF / لیبل)

بعد از «محاسبهٔ چیدمان» یک نوار ابزار خروجی بالای نقشه ظاهر می‌شود. اگر داده‌ها
بعد از محاسبه تغییر کرده باشند (نتیجه «قدیمی» باشد) خروجی‌ها غیرفعال می‌شوند تا
خروجی اشتباه به کارگاه نرود. همهٔ خروجی‌ها از همان اسنپ‌شات لحظهٔ محاسبه ساخته
می‌شوند و نگاشت لبه‌ها (با احتساب چرخش) از ماژول مشترک `src/partEdges.ts` می‌آید.

### ۱) پرینت نقشه (PDF/Print)

- با `window.print()` نیتیو مرورگر؛ بدون کتابخانه. برای PDF کافی است در دیالوگ
  چاپ «Save as PDF» انتخاب شود.
- سند چاپی در یک **Print Portal** روی `body` رندر و روی صفحه مخفی است؛ در حالت
  چاپ (`html[data-print-mode]` + `@media print` در `index.css`) کل اپ مخفی و فقط
  سند چاپی (سربرگ خلاصه + نقشه‌ها + فهرست قطعات) چاپ می‌شود. پرینت دستی با Ctrl+P
  دست نمی‌خورد.
- خروجی سیاه‌وسفید و هاشورها با `print-color-adjust: exact` حفظ می‌شوند. سند نقشه
  روی **یک برگهٔ A4 عمودی** (`@page { size: A4; margin: 5mm }`) تنظیم شده است:
  نقشه با `zoom` و ارتفاع محدود، فونت جدول و فاصله‌ها فشرده می‌شوند تا سربرگ +
  همهٔ نقشه‌ها + فهرست قطعات + فاکتور متریال در همان یک صفحه بمانند و
  `page-break-inside: avoid` از شکستن وسط کار جلوگیری می‌کند.
- در دکمهٔ واحد **«چاپ نقشه و لیست قطعات»**، زیر همهٔ SVGهای نقشه **جدول
  گروه‌بندی‌شدهٔ قطعات** (تعداد، ورق‌ها، کدهای نقشه، شرح عملیات و مربع تیک) و سپس
  **فاکتور متریال مصرفی** در همان سند چاپ می‌شود. جدول با `table-header-group` و
  `break-inside: avoid` روی ردیف‌ها، در صورت طولانی‌بودن بدون به‌هم‌ریختگی به صفحهٔ
  بعد ادامه می‌یابد و عنوان/فاکتور از جدول جدا نمی‌شوند.

### ۲) خروجی DXF برای CNC — `src/exportDxf.ts`

- تولیدکنندهٔ متنی سبک **DXF R12 (AC1009)** بدون وابستگی خارجی؛ واحد میلی‌متر.
- هر قطعه یک `POLYLINE` بسته در لایهٔ `CUT` است؛ کادر ورق‌ها در `SHEET` (چند ورق با
  فاصلهٔ ۱۰۰ میلی‌متر کنار هم + عنوان `SHEET n`)، خطوط شیار در `GROOVE` (موازی لبه،
  فاصلهٔ ۲۰ میلی‌متر داخل قطعه) و خط مورب ۴۵° در مثلث گوشه‌های لبهٔ فارسی در `FARSI_45`.
- کد هر قطعه (مثل `S1-03`) در مرکزش و در لایهٔ `LABEL` نوشته می‌شود؛ همان کدی که
  روی لیبل چاپی می‌آید. متن‌های DXF فقط ASCII است (نام فارسی در DXF امن نیست).
- «نوار» عمداً هندسهٔ DXF ندارد (عملیات برش نیست و خط روى لبه ممکن است اشتباه
  ماشین‌کاری شود)؛ جایش روی نقشهٔ چاپی و لیبل است.
- مختصات به دستگاه CNC تبدیل می‌شود: مبدأ هر ورق گوشهٔ پایین-چپ و Y رو به بالا
  (`dxfY = stockWidth - y - height`)؛ لبه‌ها بعد از تبدیل سر جای فیزیکی خودشان‌اند.

### ۳) لیبل قطعات — `src/components/LabelSheet.tsx`

- شبکهٔ **۳ ستون × ۵ ردیف در هر A4 عمودی (Portrait)**؛ هر ۱۵ لیبل یک صفحه با
  `break-after: page` جدا می‌شود و خانه‌های خالی صفحهٔ آخر برای تراز کاغذ برچسبی
  خالی می‌مانند.
- هر لیبل: کد قطعه، نام، ابعاد قطعه (+ ابعاد چرخیده روی نقشه اگر چرخیده)، شمارهٔ
  ورق و نمونه، مختصات روی ورق، علائم متنی هر عملیات («نوار: طول و عرض»،
  «فارسی ۴۵°: فقط طول»، «شیار: ندارد» و…) و یک شماتیک کوچک از لبه‌ها با همان
  نگاشت عملیات و چرخشِ نقشه.
- دکمه‌های «چاپ لیبل‌ها» (همان Print Portal، حالت labels) و «پیش‌نمایش لیبل‌ها»
  برای دیدن همان سند روی صفحه قبل از چاپ وجود دارد.

### ۴) برگهٔ کنترل تولید — `src/components/ControlSheet.tsx`

- برگهٔ روی‌صفحه همان جدول کنترلی است: هر قطعهٔ چیده‌شده یک ردیف مستقل با کد مشترک
  نقشه/لیبل، ابعاد، ورق، مختصات، چرخش و **شرح عملیات متنی** دارد؛ هر ردیف یک مربع
  خالی بزرگ برای تیک کنترل کارگاهی دارد.
- همین جدول در سند چاپی نقشه (با دکمهٔ «چاپ نقشه و لیست قطعات») به شکل
  **گروه‌بندی‌شده** هم می‌آید: قطعات هم‌نام/هم‌ابعاد با شرح عملیات یکسان در یک ردیف با
  ستون تعداد و فهرست کدهای نقشه جمع می‌شوند. دکمهٔ جداگانهٔ «چاپ برگه کنترل» حذف شده
  است تا اپراتور همه‌چیز را یک‌جا بگیرد.
- فاکتور تخمینی متریال در انتهای برگه و انتهای سند چاپی، متراژ کل نوار، لبهٔ فارسی و
  شیار را بر حسب متر با احتساب مقدار ۰/۱/۲، ابعاد و تعداد هر قطعه نشان می‌دهد.

## فاز ۵ — مدیریت پروژه‌ها (Save / Load / Manage)

مدل پروژه در `src/types/project.ts` و لایهٔ ذخیره‌سازی در `src/storage/projects.ts`:

```ts
interface Project {
  id: string;
  name: string;
  createdAt: number;
  updatedAt: number;
  parts: CutPart[];
  settings: { stockLength: number; stockWidth: number; kerf: number; allowRotation: boolean };
  lastLayout?: LayoutResult;   // آخرین نقشهٔ محاسبه‌شده (بازشدن فوری بدون محاسبهٔ مجدد)
  lastLayoutParts?: CutPart[]; // اسنپ‌شات قطعات همان محاسبه (مبنای علائم نقشه)
}
```

- **ذخیره‌سازی:** فهرست پروژه‌ها در `localStorage` با کلید **`acut_projects`**.
  علاوه بر آن، فضای کاری فعلی به‌صورت خودکار در کلید `acut_draft` نگه داشته
  می‌شود تا رفرش صفحه کار جاری را از بین نبرد (با مهاجرت خودکار از کلید قدیمی
  قطعات فازهای قبل). «ذخیرهٔ پروژه» عمل صریح کاربر است و جدا از پیش‌نویس خودکار.
- **هدر برنامه:** سمت راست لوگوی A-Cut 2Dpro و اطلاعات سازنده (**عباس کروشاد** —
  اینستاگرام/تلگرام `@Webxplusx`) و سمت چپ وضعیت پروژهٔ جاری + دکمهٔ Dropdown
  «مدیریت پروژه‌ها» (ذخیره، ذخیره با نام جدید/Save As، پروژهٔ جدید، باز کردن پروژه
  و پنج پروژهٔ اخیر).
- **مودال پروژه‌ها** (`ProjectManager.tsx`): جستجو بر اساس نام؛ برای هر پروژه نام،
  تاریخ آخرین ویرایش، تعداد ردیف/قطعه، ابعاد ورق و نشان «دارای نقشهٔ برش» نمایش
  داده می‌شود و دکمه‌های [باز کردن] و [حذف] دارد. حذف و بازکردن/پروژهٔ جدید هنگام
  داشتن تغییرات ذخیره‌نشده ابتدا تأییدیه می‌گیرد.
- **باز کردن پروژه** همهٔ Stateها را برمی‌گرداند (قطعات، تنظیمات ورق و تیغه،
  گزینهٔ چرخش) و اگر `lastLayout` ذخیره شده باشد نقشهٔ برش بلافاصله رندر می‌شود؛
  امضای آن از روی اسنپ‌شات ذخیره‌شده بازسازی می‌شود تا برچسب «نتیجهٔ قدیمی»
  دقیقاً مثل قبل از ذخیره رفتار کند.
- **تغییرات ذخیره‌نشده (Dirty):** با مقایسهٔ امضای فضای کاری با آخرین وضعیت
  ذخیره‌شده تشخیص داده می‌شود؛ در هدر و منو با نشان کهربایی دیده می‌شود و هنگام
  بستن/رفرش صفحه، `beforeunload` به کاربر هشدار می‌دهد.

## نسخه‌های بومی — اندروید (Capacitor) و ویندوز (Electron)

همان اپ React/Vite بدون تغییر منطق، داخل بستهٔ نصب‌شدنی اجرا می‌شود. تنظیمات آماده است:

- `capacitor.config.ts` — `appId: com.acut.cut2dpro`، `appName: A-Cut 2Dpro`، **`webDir: 'dist'`**
  و بخش `server` در حالت **بارگذاری زنده (Live URL)**: اپ اندروید پوسته‌ای است که همیشه
  آخرین نسخهٔ وب (`https://gase99.github.io/Webxplusx/`) را بارگذاری می‌کند؛ اگر بارگذاری
  موفق نباشد (مثلاً بدون اینترنت)، صفحهٔ خطای محلی `public/offline.html` (از طریق
  `server.errorPath`) نمایش داده می‌شود.
- `android/` — پروژهٔ کامل اندروید (Capacitor 8، `minSdk 24`، `targetSdk 36`، `applicationId com.acut.cut2dpro`)،
  آیکون لانچر و Splash با رنگ برند `#0284C7`، پشتیبانی RTL.
- `desktop/` — بستهٔ Electron: `main.cjs` (سرو محتوای `web/` روی پروتکل امن `app://` +
  متد `checkForUpdates` برای بروزرسانی خودکار با `electron-updater`)، `prepare.mjs`
  (کپی `dist` → `desktop/web`)، و پیکربندی `electron-builder` برای خروجی **اینستالر NSIS**
  با نام `A-Cut-2Dpro-<نسخه>-Setup.exe` به‌همراه `latest.yml` و `blockmap` برای آپدیت خودکار
  از GitHub Releases.

> نکته: `base` در `vite.config.ts` برای وب `'/Webxplusx/'` و برای بستهٔ بومی `'./'` است؛
> بدون این تفاوت، فایل‌های JS/CSS داخل WebView/Electron پیدا نمی‌شدند.
> در اندروید، به‌دلیل Live URL، نسخهٔ در حال اجرا همان بیلد وب است و نسخهٔ داخل APK فقط
> برای صفحهٔ خطای آفلاین نگه داشته می‌شود؛ در ویندوز محتوای `dist` واقعاً داخل خود EXE است.

### ۱) ساخت فایل نصبی اندروید (`.apk`)

**پیش‌نیازها:** Node.js 20+، **JDK 21**، Android SDK (از طریق Android Studio → SDK Manager:
`Android SDK Platform 36` + `Build-Tools` + `Platform-Tools`) و متغیر محیطی `ANDROID_HOME`.

**روش الف — خط فرمان (سریع‌ترین):**

```bash
npm install
npm run build:app          # خروجی Vite با base نسبی
npx cap sync android       # کپی dist داخل android/app/src/main/assets/public

cd android
./gradlew assembleDebug     # لینوکس/مک   (ویندوز: gradlew.bat assembleDebug)
```
خروجی قابل نصب:
`android/app/build/outputs/apk/debug/app-debug.apk`
(یا از ریشه: `npm run android:apk`)

**روش ب — Android Studio (ساده‌ترین برای امضاشده):**

```bash
npm run android:open
```
سپس در Android Studio: `Build → Build Bundle(s) / APK(s) → Build APK(s)`.
فایل در `android/app/build/outputs/apk/debug/` ساخته می‌شود. برای نسخهٔ Release:
`Build → Generate Signed Bundle / APK…` و انتخاب Keystore خودتان (فایل `.jks` را
هرگز کامیت نکنید؛ در `.gitignore` هست).

نصب روی گوشی: فایل `.apk` را منتقل و «نصب از منابع نامشخص» را برای فایل‌منیجر فعال کنید،
یا با کابل: `adb install -r android/app/build/outputs/apk/debug/app-debug.apk`.

**بعد از هر تغییر کد:** به‌لطف Live URL، تغییرات رابط و منطق برنامه با همان انتشار نسخهٔ وب
به کاربران اندروید می‌رسد و به APK جدید نیازی نیست. ساخت APK تازه فقط وقتی لازم است که
خود پوستهٔ بومی عوض شود (`capacitor.config.ts`، پلاگین‌ها، `public/offline.html` یا
پروژهٔ `android/`): `npm run android:apk` (+ افزایش `versionCode` در `android/app/build.gradle`).
دوباره `cap add` هم لازم نیست.

### ۲) ساخت فایل نصبی ویندوز (اینستالر NSIS با بروزرسانی خودکار)

**پیش‌نیازها:** Node.js 20+ و ویندوز ۱۰/۱۱ (پیشنهاد). ساخت EXE روی ویندوز بدون
هیچ ابزار اضافه‌ای انجام می‌شود؛ روی لینوکس/مک به `wine` نیاز است.

از نسخهٔ ۰٫۲٫۰ خروجی ویندوز دیگر Portable تک‌فایل نیست؛ `electron-updater` از Portable
پشتیبانی نمی‌کند، پس اینستالر **NSIS** (نصب تک‌کلیکهٔ per-user، بدون نیاز به ادمین)
جای آن را گرفت تا برنامه بتواند خودش را آپدیت کند.

```bash
npm install
npm run desktop:install     # نصب electron + electron-builder + electron-updater داخل desktop/
npm run build:win           # بیلد وب + کپی به desktop/web + ساخت اینستالر NSIS
```
خروجی در `desktop/release/`:
- `A-Cut-2Dpro-<نسخه>-Setup.exe` — فایل نصب (همان که کاربر بار اول دانلود می‌کند)
- `latest.yml` — متادیتای آخرین نسخه؛ `electron-updater` روی سیستم کاربران همین فایل را
  از آخرین GitHub Release می‌خواند
- `A-Cut-2Dpro-<نسخه>-Setup.exe.blockmap` — نقشهٔ بلوک‌ها برای دانلود تفاضلی آپدیت‌ها

**رفتار آپدیت در برنامه:** `checkForUpdates()` در `desktop/main.cjs` پنج ثانیه بعد از اجرا
(و هر ۴ ساعت) ریلیزهای گیت‌هاب را چک می‌کند؛ نسخهٔ جدید بی‌صدا در پس‌زمینه دانلود می‌شود و
بعد از اتمام دانلود پیام «نسخهٔ جدید دانلود شد؛ برای نصب ری‌استارت شود؟» می‌آید. انتخاب
«بعداً» یعنی نصب خودکار هنگام بستن برنامه (`autoInstallOnAppQuit`).

برای تست بدون ساخت EXE:
```bash
npm run desktop:dev         # پنجرهٔ Electron با همان بیلد
```

- ساخت فقط پوشهٔ اجرایی (بدون installer): `cd desktop && npm run pack:dir`
- امضای دیجیتال ویندوز (اختیاری): متغیرهای `CSC_LINK` و `CSC_KEY_PASSWORD` را تنظیم کنید.

### ۳) ساخت خودکار با GitHub Actions (بدون نصب ابزار روی سیستم شما)

دو ورک‌فلوی آماده است:

- **Build Android APK** (`.github/workflows/build-android.yml`) → artifact با نام
  `a-cut-2dpro-debug-apk`؛ با `Actions → Build Android APK → Run workflow` دستی اجرا
  می‌شود و با هر تغییر در `android/**`، `capacitor.config.ts`، `vite.config.ts`،
  `package*.json` یا خودِ فایل ورک‌فلو روی `main` و همچنین پوش تگ `v*` خودکار اجرا می‌شود.
- **Build Windows Installer (NSIS)** (`.github/workflows/windows-exe.yml`) → artifact با
  نام `a-cut-2dpro-windows-installer` (Setup.exe + ‏`latest.yml` + ‏`blockmap`)؛
  با پوش تگ `v*` علاوه بر آن، **GitHub Release** منتشر می‌شود تا آپدیت خودکار
  نسخه‌های نصب‌شده کار کند (اجرای دستی فقط artifact می‌سازد).

> نکته: در مرحلهٔ `Set up Android SDK` باید `packages: 'platform-tools'` تنظیم شود؛
> مقدار پیش‌فرض این اکشن (`tools platform-tools`) شامل پکیج منسوخ `tools` است که
> گوگل آن را از مخازن حذف کرده و باعث خطای ورک‌فلو می‌شود.

### ۴) روند انتشار نسخهٔ جدید (چک‌لیست)

1. نسخه را در **هر دو** `package.json` (ریشه) و `desktop/package.json` بالا ببرید
   (مثلاً `0.2.0` → `0.3.0`) و با `npm install --package-lock-only` لاک‌فایل‌ها را همگام کنید.
2. تغییرات را به `main` مرج کنید → نسخهٔ وب روی GitHub Pages منتشر می‌شود:
   - **وب/PWA:** کاربران پیام «نسخهٔ جدید برنامه آماده است» را می‌بینند و با یک کلیک
     بروز می‌شوند (`src/components/UpdateToast.tsx` + سرویس‌ورکر در حالت `prompt`).
   - **اندروید:** اپ (Live URL) همان لحظه نسخهٔ جدید وب را نشان می‌دهد؛ هیچ کاری لازم نیست.
3. برای ویندوز تگ بزنید و پوش کنید: `git tag v0.3.0 && git push origin v0.3.0` → ورک‌فلوی
   NSIS فایل نصب + `latest.yml` را در GitHub Release منتشر می‌کند:
   - **ویندوز:** برنامه‌های نصب‌شده در اجرای بعدی، آپدیت را خودکار در پس‌زمینه دانلود و
     با تأیید کاربر (یا هنگام خروج) نصب می‌کنند.
4. APK اندروید فقط وقتی دوباره لازم می‌شود که پوستهٔ بومی تغییر کرده باشد؛ در آن صورت
   `versionCode` را در `android/app/build.gradle` یکی بالا ببرید تا روی نسخهٔ قبلی نصب شود.
